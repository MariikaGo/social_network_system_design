# Social Network System Design

Учебное REST API социальной сети наподобие VK. Контракт находится в [api/rest_api.yml](api/rest_api.yml), версия OpenAPI — **3.0.3**. Это описание будущего сервера, а не реализованный Go backend. Адрес `https://api.example.com/v1` условный.

## Допущения задания

- Все запросы требуют `Authorization: Bearer <token>`. Сервер проверяет токен и узнаёт текущего пользователя. Получение токена вне задания.
- Дружба сразу взаимная, без заявок. Добавление и удаление меняют отношение для обеих сторон в одной транзакции.
- Профили, списки друзей и посты доступны всем авторизованным пользователям. Приватность и блокировки вне задания.
- Сообщения отправляются в уже существующие чаты. Доступ есть только у участников. Создание чата вне задания.
- «Чтение сообщений» означает получение истории. Отметки «прочитано» здесь не реализуются: GET не меняет состояние.
- Медиа сначала загружаются отдельно, затем их идентификаторы передаются при публикации поста.
- Идентификаторы — UUID, даты — RFC 3339 в UTC. Автор и отправитель всегда берутся из токена, не из тела запроса.

## Операции

Все пути ниже идут после `/v1`.

| Метод и путь | Назначение | Успех |
| --- | --- | --- |
| `PUT /me/friends/{friend_id}` | Добавить друга | 204 |
| `DELETE /me/friends/{friend_id}` | Удалить друга | 204 |
| `GET /users/{user_id}/friends` | Список друзей пользователя | 200 |
| `GET /users/{user_id}` | Профиль пользователя | 200 |
| `POST /media` | Загрузить один файл | 201 |
| `POST /posts` | Опубликовать пост | 201 |
| `GET /me/feed` | Домашняя лента | 200 |
| `GET /users/{user_id}/posts` | Посты конкретного автора | 200 |
| `GET /me/chats` | Список моих чатов и диалогов | 200 |
| `POST /chats/{chat_id}/messages` | Отправить сообщение | 201 |
| `GET /chats/{chat_id}/messages` | Получить историю сообщений | 200 |

### Друзья и профиль

В `/me/friends/{friend_id}` идентификатор обозначает человека, с которым мы устанавливаем связь. Например, `PUT /me/friends/22222222-2222-4222-8222-222222222222` добавляет этого человека в друзья текущему пользователю. Искать пользователя по имени в этой операции не нужно: клиент уже получил его id, например из профиля. Поиск пользователей — отдельная задача вне этого контракта.

Выбран PUT: адрес связи заранее известен, повторный запрос не создаёт вторую дружбу. Возвращаем 204 и при первом добавлении, и при повторном. DELETE тоже возвращает 204, если связи уже нет. Себя добавить нельзя — 400. Если целевого пользователя не существует — 404.

`GET /users/{user_id}` возвращает профиль, а `/friends` — коллекцию профилей друзей. Существующий пользователь без друзей получает 200 и пустой массив, потому что отсутствие элементов не является ошибкой.

### Посты и медиа

Сначала `POST /media` принимает `multipart/form-data` с полем `file`. Разрешены JPEG, PNG и MP4 до 20 МиБ (20 971 520 байт). Сервер проверяет реальное содержимое и размер, сохраняет файл и возвращает объект Media с `id`. В этом учебном варианте загрузка синхронная: ответ означает, что файл уже доступен.

Затем `POST /posts` принимает JSON:

```json
{
  "text": "Мой первый пост",
  "media_ids": ["11111111-1111-4111-8111-111111111111"]
}
```

Допустим пост только с текстом или только с медиа. Пустой объект и текст из пробелов запрещены. Максимум 10 вложений и 10 000 символов текста. Если передано поле `media_ids`, оно должно содержать хотя бы один id. Медиа должны принадлежать автору, существовать и ещё не быть привязаны. Одно медиа используется только в одном посте. Создание поста и привязка выполняются атомарно, чтобы два запроса не смогли занять одно вложение.

Ответ 201 содержит созданный Post, включая id, автора, дату и вложения с URL. Бинарный файл не передаётся внутри JSON. Очистка загруженных, но не использованных файлов — отдельная фоновая задача вне задания.

### Домашняя лента и стена

`GET /me/feed` возвращает мои посты и посты моих текущих друзей. Здесь нет алгоритма рекомендаций. `GET /users/{user_id}/posts` возвращает посты одного автора. Обе коллекции сортируются по `created_at DESC, id DESC`: свежие записи первыми, id разрешает совпадение времени.

### Чаты и сообщения

`GET /me/chats` возвращает только чаты текущего пользователя. Диалог двух людей — такой же Chat. Чаты сортируются по `updated_at DESC, id DESC`; у пустого чата поле `last_message` отсутствует.

`POST /chats/{chat_id}/messages` принимает `{"text":"Привет!"}` и возвращает Message с кодом 201. Текст непустой, до 4 000 символов. Сервер проверяет участие в чате. Сохранение сообщения и обновление времени активности чата выполняются в одной транзакции. Повторный POST может создать второе сообщение: ключ идемпотентности вне задания.

`GET /chats/{chat_id}/messages` возвращает историю, новые сообщения первыми (`created_at DESC, id DESC`). Интерфейс при необходимости разворачивает страницу для показа сверху вниз. Несуществующий чат даёт 404, существующий чужой — 403.

## Пагинация

У всех списков есть `limit` (по умолчанию 20, от 1 до 100) и `offset` (по умолчанию 0, неотрицательный). Например: `GET /me/feed?limit=20&offset=20`.

```json
{
  "items": [],
  "page": {"limit": 20, "offset": 20, "has_more": false}
}
```

Следующая страница: `offset + limit`. Сервер запрашивает `limit + 1` элементов, чтобы вычислить `has_more`, а возвращает не больше `limit`. Если элементов нет, возвращается 200 и `items: []`. Полный `total` не рассчитываем. Список друзей сортируется по id ASC, остальные порядки описаны выше. Между запросами данные могут измениться: offset-пагинация допускает повторы и пропуски. Для большой активной ленты следующим шагом станет курсорная пагинация.

## Ответы и ошибки

- **200** — данные получены, даже если список пуст.
- **201** — создан пост, файл или сообщение; тело содержит созданный ресурс.
- **204** — операция выполнена, тела ответа нет.
- **400** — неверный UUID, параметры, JSON или нарушены правила запроса.
- **401** — нет действительного токена.
- **403** — нет права на чат или чужое медиа.
- **404** — пользователь, чат или медиа не существует.
- **409** — медиа уже привязано к посту.
- **413** — файл слишком большой.
- **415** — неподдерживаемый формат тела или файла.

Ошибки имеют общий формат:

```json
{"code": "not_found", "message": "Ресурс не найден"}
```

Спецификация описывает ожидаемые ошибки каждой операции. Непредвиденные сбои сервера обрабатываются общим middleware; отдельная модель инфраструктурных ошибок здесь не проектируется.

## Как читать YAML

- `openapi` — версия стандарта; `info` — название и версия нашего API.
- `servers` — базовый адрес; `paths` — пути и HTTP-методы.
- `parameters` — значения в пути (`user_id`) и строке запроса (`limit`). В шаблоне пишется `{user_id}`, без `$`.
- `requestBody` — данные, которые клиент отправляет: JSON или файл.
- `responses` — возможные ответы с кодами и структурами данных.
- `components.schemas` — общие модели User, Post, Media, Chat, Message, страницы и ошибки.
- `$ref` — ссылка на уже описанную модель. Например, `#/components/schemas/User` означает «используй User из components», а не внешний HTTP-запрос.
- `required` задаёт обязательные поля; `example` показывает пример, но не значение по умолчанию.
- `securitySchemes` описывает Bearer-аутентификацию, а корневой `security` применяет её ко всем операциям.

OpenAPI — сам контракт. Swagger UI — один из инструментов, который показывает его как интерактивную документацию. YAML может писать Go-разработчик вместе с командой; иногда его генерируют из кода. Здесь выбран подход «сначала контракт»: заранее договариваемся с клиентом о запросах и ответах. Справочник: [OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3).

## Как это перейдёт в Go backend

Для каждой операции нужен маршрут и обработчик. Например, `createPost` соответствует обработчику POST `/posts`. Middleware проверяет токен и помещает user id в context. Обработчик разбирает JSON в структуру запроса, проверяет ограничения и вызывает сервис. Сервис проверяет бизнес-правила и обращается к хранилищу; обработчик преобразует результат в HTTP-ответ.

Поле `media_ids` станет полем структуры с тегом `json:"media_ids"`. `$ref` помогает переиспользовать описание типов, но сам по себе не создаёт Go-структуры и не исполняет валидацию. Ограничения `maxLength`, владение медиа и участие в чате нужно реализовать на сервере. Для необязательного текста полезен `*string`, если требуется различать отсутствие поля и пустую строку. Даты удобно представлять `time.Time`; длину текста считать в символах, а не байтах UTF-8.

Пример запроса к будущему серверу:

```sh
curl -X POST 'https://api.example.com/v1/posts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  -d '{"text":"Изучаю Go"}'
```

Это задание покрывает REST-контракт. База данных, масштабирование, очереди, WebSocket, авторизация с выдачей токенов и полноценная архитектура сервиса потребуют отдельного проектирования.

## Проверка

Из корня репозитория можно повторить проверку в отдельном окружении:

```sh
python3 -m venv /tmp/social-api-check
/tmp/social-api-check/bin/pip install openapi-spec-validator==0.9.0
/tmp/social-api-check/bin/openapi-spec-validator api/rest_api.yml
```

Валидатор проверяет структуру OpenAPI и ссылки. Он не доказывает, что будущий сервер соблюдает контракт. Примеры моделей дополнительно проверены по схемам; поведение Go-сервера нужно будет проверить после реализации.
